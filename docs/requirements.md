# Требования

## Участники

- **Студент** — автор PR с учебной работой
- **Преподаватель** — настраивает проверки и смотрит результаты
- **Клиент API** — GitHub Actions или скрипт, который ставит проверку от имени преподавателя
- **GitHub** — внешняя система: оттуда берутся файлы PR, туда пишется комментарий

## Сценарий 1. Постановка проверки и успешный результат

**Цель:** автоматически проверить формальную часть работы и сообщить результат в PR.
**Участник:** клиент API, студент.

**Основной поток:**

1. Студент открывает PR с работой
2. Клиент API отправляет `POST /checks` с полями `repo`, `pr_number`, `checks` и заголовком `Idempotency-Key`
3. Сервис проверяет запрос, создаёт Проверку в состоянии `queued` и возвращает `201` с её `id`
4. Диспетчер переводит Проверку в `running` и вызывает исполнителя для каждой проверки из списка
5. Каждый исполнитель получает файлы PR через GitHub API и возвращает ToolResult со статусом `passed`
6. Сервис сохраняет результаты и переводит Проверку в `passed`
7. Сервис пишет в PR комментарий "Проверка пройдена" со списком выполненных проверок

**Критерии приёмки:**

- **Дано** PR со всеми нужными файлами и заполненными разделами, **когда** клиент отправляет `POST /checks` с проверками `structure` и `sections`, **тогда** ответ `201`, в теле `id` и `status = queued`
- **Дано** Проверка в состоянии `running`, **когда** все исполнители вернули `passed`, **тогда** Проверка в состоянии `passed` и у неё 2 ToolResult со статусом `passed`
- **Дано** Проверка перешла в `passed`, **когда** сервис завершил обработку, **тогда** в PR появился ровно один комментарий с результатом
- **Дано** Проверка существует, **когда** клиент отправляет `GET /checks/{id}`, **тогда** ответ `200` с текущим состоянием и результатом по каждой проверке

## Сценарий 2. Работа не прошла проверку

**Цель:** показать студенту, что именно нужно исправить.
**Участник:** студент, клиент API.

**Основной поток:**

1. Клиент API ставит проверку, как в сценарии 1
2. Исполнитель `structure` находит файл вне папки студента, исполнитель `sections` находит пустой раздел
3. Каждый из них возвращает ToolResult со статусом `failed` и списком проблем: путь файла и описание
4. Сервис переводит Проверку в `failed`
5. Сервис пишет в PR комментарий со списком всех проблем
6. Студент исправляет работу и пушит в ту же ветку, клиент ставит новую Проверку

**Критерии приёмки:**

- **Дано** в PR есть файл вне разрешённой папки, **когда** выполняется проверка `structure`, **тогда** ToolResult `failed` содержит путь этого файла и описание "файл вне вашей папки"
- **Дано** один исполнитель вернул `failed`, остальные `passed`, **когда** все исполнители завершились, **тогда** Проверка в состоянии `failed`
- **Дано** один исполнитель вернул `failed`, другой `error`, **когда** все исполнители завершились, **тогда** Проверка в состоянии `error`: ошибка выполнения важнее непройденной проверки
- **Дано** один исполнитель вернул `failed`, **когда** остальные ещё не выполнены, **тогда** они всё равно выполняются до конца
- **Дано** Проверка в `failed`, **когда** сервис пишет комментарий, **тогда** в нём перечислены все проблемы всех исполнителей, а не только первая

## Сценарий 3. Повторный запрос с тем же ключом идемпотентности

**Цель:** не создавать дубли проверок, если клиент повторил запрос, например после обрыва сети.
**Участник:** клиент API.

**Основной поток:**

1. Клиент отправляет `POST /checks` с `Idempotency-Key = K`
2. Сервис создаёт Проверку и возвращает `201`
3. Ответ теряется из-за обрыва сети, клиент повторяет тот же запрос с тем же `K`
4. Сервис находит Проверку с ключом `K` и возвращает её с кодом `200`, новую не создаёт

**Критерии приёмки:**

- **Дано** Проверка с ключом `K` уже создана, **когда** приходит `POST /checks` с тем же `K` и тем же телом, **тогда** ответ `200` с `id` существующей Проверки, число Проверок в хранилище не изменилось
- **Дано** Проверка с ключом `K` уже создана, **когда** приходит `POST /checks` с тем же `K`, но другим телом, **тогда** ответ `409` с кодом `idempotency_conflict`
- **Дано** запрос без заголовка `Idempotency-Key`, **когда** клиент отправляет `POST /checks`, **тогда** ответ `400` с кодом `missing_idempotency_key`

## Жизненный цикл Проверки (Job)

**Состояния:**

- `queued` — поставлена в очередь
- `running` — выполняется
- `passed` — пройдена: все исполнители вернули `passed`
- `failed` — не пройдена: хотя бы один исполнитель вернул `failed`
- `error` — не удалось выполнить, например GitHub недоступен
- `cancelled` — отменена

**Разрешённые переходы:**

- `queued → running` — диспетчер взял Проверку в работу
- `queued → cancelled` — отмена до начала выполнения
- `running → passed`
- `running → failed`
- `running → error`
- `running → cancelled` — отмена во время выполнения

**Итоговые состояния:** `passed`, `failed`, `error`, `cancelled`. Из них переходов нет.

## Единый формат ошибки

Все ошибки API возвращаются в одном формате:

```json
{"error": {"code": "unknown_check", "message": "Неизвестная проверка: spellcheck", "details": {"check": "spellcheck"}}}
```

## Сценарий 4. Неизвестная проверка в запросе (ошибочный)

**Цель:** отклонить некорректный запрос до создания Проверки.
**Участник:** клиент API.

**Основной поток:**

1. Клиент отправляет `POST /checks` с `checks = ["structure", "spellcheck"]`
2. Сервис ищет каждую проверку в реестре, `spellcheck` не найдена
3. Сервис возвращает `400` и не создаёт Проверку

**Критерии приёмки:**

- **Дано** в реестре нет проверки `spellcheck`, **когда** клиент отправляет `POST /checks` со `spellcheck` в списке, **тогда** ответ `400` с кодом `unknown_check`, в `details` имя `spellcheck`
- **Дано** такой же запрос, **когда** сервис его отклонил, **тогда** в хранилище не появилось новой Проверки
- **Дано** список `checks` пустой или `pr_number` не число, **когда** клиент отправляет `POST /checks`, **тогда** ответ `400` с кодом `validation_error` и именем неверного поля в `details`

## Сценарий 5. GitHub недоступен (ошибочный)

**Цель:** корректно завершить проверку, если внешняя система не отвечает или отвечает мусором.
**Участник:** клиент API, GitHub.

**Основной поток:**

1. Проверка переходит в `running`
2. Исполнитель запрашивает файлы PR через адаптер GitHub API
3. GitHub не отвечает за 5 секунд или возвращает ошибку `5xx`
4. Адаптер повторяет запрос, всего не больше 3 попыток с паузой между ними
5. Все попытки неудачны, исполнитель возвращает ToolResult со статусом `error` и причиной
6. Сервис переводит Проверку в `error`

**Критерии приёмки:**

- **Дано** GitHub отвечает дольше 5 секунд, **когда** адаптер запрашивает файлы, **тогда** запрос прерывается по timeout и повторяется, всего не больше 3 попыток
- **Дано** все 3 попытки неудачны, **когда** адаптер вернул ошибку, **тогда** Проверка в состоянии `error` с причиной `github_unavailable`
- **Дано** GitHub ответил `503` на первую попытку и `200` на вторую, **когда** адаптер получил ответ, **тогда** проверка продолжается и завершается как обычно
- **Дано** GitHub вернул `404`, PR не найден, **когда** адаптер получил ответ, **тогда** повторов нет, Проверка в `error` с причиной `pr_not_found`
- **Дано** GitHub вернул `200`, но тело не JSON, **когда** адаптер разбирает ответ, **тогда** сервис не падает, Проверка в `error` с причиной `bad_github_response`

## Сценарий 6. Отмена проверки

**Цель:** не тратить ресурсы на устаревшую проверку, например когда студент запушил новый коммит.
**Участник:** клиент API.

**Основной поток:**

1. Клиент отправляет `POST /checks/{id}/cancel`
2. Проверка в `queued` или `running`: сервис переводит её в `cancelled`, незавершённые исполнители не запускаются, комментарий в PR не пишется
3. Ответ `200` с состоянием `cancelled`

**Ошибочный поток:** Проверка уже в итоговом состоянии, сервис отвечает `409 invalid_transition`.

**Критерии приёмки:**

- **Дано** Проверка в `queued`, **когда** клиент отправляет cancel, **тогда** ответ `200`, состояние `cancelled`, исполнители не запускались
- **Дано** Проверка в `running`, **когда** клиент отправляет cancel, **тогда** состояние `cancelled`, комментарий в PR не пишется
- **Дано** Проверка в `passed`, **когда** клиент отправляет cancel, **тогда** ответ `409` с кодом `invalid_transition`, состояние не изменилось
- **Дано** Проверки с таким `id` нет, **когда** клиент отправляет cancel, **тогда** ответ `404` с кодом `check_not_found`

## Что предложил ИИ

**Модель:** Claude

**Промпт:**

```
Ты опытный инженер по тестированию. Вот основной сценарий нашего сервиса
автопроверки учебных работ:

[текст сценария 1 из этого документа]

Найди 3 способа сломать этот сценарий, которые мы не учли.
Для каждого опиши, что произойдёт и как это обработать.
```

**Предложения и решения:**

1. **GitHub отвечает `200`, но в теле HTML-страница вместо JSON**, например при сбое прокси. Сервис упадёт при разборе ответа, Проверка зависнет в `running`.
   **Приняли.** Добавили критерий в сценарий 5: такой ответ даёт `error` с причиной `bad_github_response`.

2. **В PR больше 30 файлов, GitHub API отдаёт список постранично.** Если не обходить все страницы, проверка `structure` увидит только первую страницу и пропустит нарушения, Проверка ошибочно станет `passed`.
   **Приняли.** Добавили задачу в backlog: адаптер GitHub обходит все страницы списка файлов.

3. **Комментарий в PR не удалось опубликовать**, например у токена нет прав на запись. Модель предложила переводить Проверку в `error`.
   **Не приняли.** Результат проверки уже получен и сохранён, и он верный, ошибка только в доставке. Проверка остаётся в итоговом состоянии, сбой публикации пишем в лог и отдаём в `GET /checks/{id}` поле `comment_published = false`.
