# Проверка контракта колодой

Прошли по контракту картами К1–К10 из [колоды практики 2](https://github.com/AIProgramIngeneering2026/Zadania/blob/main/tasks/p2_poker/README.md#колода). Для каждой карты — ответ и место, где он записан.

## Карты

| Карта | Ситуация в AutoCheck | Ответ контракта |
|---|---|---|
| К1 Двойной клик | GitHub Actions дважды за 100 мс отправил `POST /checks` с одним `Idempotency-Key` | Одна Проверка. Второй запрос получает `200` с тем же `id`, при одновременной вставке спасает уникальный индекс — [ADR-0003](adr/0003-idempotency.md), [openapi.yaml](api/openapi.yaml) `POST /checks`, ответ `200` |
| К2 Ответ потерялся | Проверка создана, но клиент получил таймаут соединения | Клиент повторяет запрос с тем же ключом и получает `200` с `id` уже созданной Проверки, дубля нет — [ADR-0003](adr/0003-idempotency.md), [requirements.md](requirements.md) сценарий 3 |
| К3 Неизвестная операция | `checks: ["structure", "spellcheck"]` | `400`, код `unknown_check`, в `details.check` имя `spellcheck`, Проверка не создаётся — [openapi.yaml](api/openapi.yaml) `components.responses.BadRequest`, [requirements.md](requirements.md) сценарий 4 |
| К4 Кривые параметры | Нет `repo`, `pr_number: "abc"`, `params.structure.root` без слеша в конце | `400`, код `validation_error`, в `details.field` поле: `repo`, `pr_number`, `params.structure.root`. Параметры Tool проверяет вызывающий до создания Проверки — [openapi.yaml](api/openapi.yaml) `CheckCreate`, [tool-contract.md](tool-contract.md) "Кто проверяет параметры" |
| К5 Воскрешение | Клиент хочет перезапустить Проверку в `failed` после исправления работы | Перезапуска нет: из итоговых состояний переходов нет. Новый `POST /checks` с новым ключом создаёт новую Проверку, старая с результатами остаётся без изменений — [job-states.md](job-states.md) "Запрещённые переходы" |
| К6 Отмена | Студент запушил новый коммит, клиент отменяет Проверку в `running` | `POST /checks/{id}/cancel` → `200`, состояние `cancelled`. Незапущенные Tool не запускаются, комментарий не пишется, результаты уже завершённых Tool сохраняются. Отмена завершённой — `409 invalid_transition` — [openapi.yaml](api/openapi.yaml) `POST /checks/{id}/cancel`, [job-states.md](job-states.md) |
| К7 Огромный вход | Тело запроса на 16 МБ или PR на 3000 файлов | Тело больше 16 КБ → `413 payload_too_large`, Проверка не создаётся. PR больше 300 файлов → Проверка в `error` с причиной `pr_too_large`. Файл больше 1 МБ `sections` пропускает **с предупреждением (Warning), которое не переводит Проверку в `failed`** — [openapi.yaml](api/openapi.yaml) `POST /checks`, ответ `413`, [tool-contract.md](tool-contract.md) "Ограничения входа" |
| К8 Чужой или несуществующий id | `GET /checks/{случайный uuid}` | Несуществующий → `404 check_not_found` без подробностей. Чужого клиента нет: клиент один, разделения по владельцам сознательно не делаем, `id` — UUID v4, перебором не подобрать — [ADR-0004](adr/0004-single-client.md), [openapi.yaml](api/openapi.yaml) `GET /checks/{id}` |
| К9 Перезапуск сервера | Сервис перезапустился, Проверка была в `running` | После старта Проверка остаётся в `running`, через 10 минут с момента перехода в `running` Worker переводит её в `error` с причиной `timeout`. Проверки в `queued` лежат в БД и будут выполнены — [ADR-0002](adr/0002-background-execution.md), [job-states.md](job-states.md) "После перезапуска сервиса" |
| К10 Внешний сервис | GitHub молчит 30 секунд, отвечает HTML вместо JSON или переименовал поле `filename` | Молчит → timeout 5 секунд, до 3 попыток, потом Проверка в `error`, причина `github_unavailable`. Мусор или нет нужного поля → без повторов `error`, причина `bad_github_response`. Клиент видит причину в `GET /checks/{id}` — [tool-contract.md](tool-contract.md) "Какими ошибками отказывает", [requirements.md](requirements.md) сценарий 5 |

## Что изменили в контракте после прохода колодой

- К7: в контракте не было ни одного ограничения на размер. Добавили предел тела 16 КБ с ответом `413`, предел 300 файлов с причиной `pr_too_large` и предел 1 МБ на файл
- К8: не было сказано, видит ли клиент чужие Проверки. Решение записали в ADR-0004
- К9: правило таймаута было только в requirements, добавили раздел про перезапуск в job-states

## Что предложил ИИ

**Модель:** Claude

**Промпт:**

```
Ты атакующий в контрактном покере. Вот контракт нашего сервиса AutoCheck:
openapi.yaml, диаграмма состояний Проверки, контракт Tool и ADR (текст ниже).
Вот колода карт К1–К10 (текст ниже).

Карты К1–К10 мы уже разыграли сами. Найди ещё 3 ситуации, на которые контракт
не отвечает или отвечает противоречиво. Для каждой: конкретный запрос или
последовательность событий, что сейчас произойдёт по контракту и почему это плохо.

[контракт]
[колода]
```

**Находки и решения:**

1. **Студент пушит новый коммит, пока Проверка выполняется.** Tool `structure` читает список файлов старого коммита, а `sections` через секунду читает файлы уже нового. Итог Проверки собран из двух разных версий работы.
   **Приняли.** При переходе в `running` адаптер фиксирует `head_sha` PR, все Tool читают файлы этого коммита. Добавили `head_sha` в схему `Check` в [openapi.yaml](api/openapi.yaml) и в `CheckContext` в [tool-contract.md](tool-contract.md).

2. **Отмена приходит, пока ResultPublisher пишет комментарий.** Комментарий "Проверка пройдена" уже в PR, а Проверка становится `cancelled`. Состояние и PR противоречат друг другу.
   **Приняли.** Зафиксировали порядок: сначала итоговое состояние сохраняется, потом публикуется комментарий. Отмена в этот момент получает `409 invalid_transition`. Добавили раздел "Порядок завершения" в [job-states.md](job-states.md).

3. **GitHub отвечает `403` с исчерпанным лимитом запросов.** Модель предложила ждать сброса лимита по заголовку `X-RateLimit-Reset` и повторять.
   **Не приняли.** Сброс лимита бывает через час, а Проверка в `running` дольше 10 минут и так уходит в `error` по таймауту. Ожидание только держало бы Проверку без пользы. Записали в [tool-contract.md](tool-contract.md): `403` с исчерпанным лимитом сразу даёт `github_unavailable` без ожидания, клиент поставит новую Проверку позже.
