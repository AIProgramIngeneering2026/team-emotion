# ADR-0003. Защита от повторного запроса ключом идемпотентности

- **Дата:** 2026-11-14
- **Статус:** принято

## Контекст и ограничения

- GitHub Actions повторяет шаг при сетевом сбое, пользователь может нажать перезапуск workflow
- Дубль Проверки означает два одинаковых комментария в PR и лишние запросы к GitHub API
- Сценарий 3 в [requirements.md](../requirements.md)

## Решение

`POST /checks` требует заголовок `Idempotency-Key`. Сервис хранит ключ, хеш тела запроса и `id` Проверки в той же таблице, на ключе стоит уникальный индекс.

- Тот же ключ и то же тело → `200` и существующая Проверка
- Тот же ключ и другое тело → `409 idempotency_conflict`
- Нет заголовка → `400 missing_idempotency_key`
- Ключ хранится 24 часа, потом удаляется, и запрос с ним создаёт новую Проверку

Два одновременных запроса с одним ключом разруливает уникальный индекс: второй получает ошибку вставки, сервис перечитывает Проверку и отвечает `200`.

## Рассмотренные альтернативы

| Вариант | Почему не выбрали |
|---|---|
| Без ключа, искать незавершённую Проверку того же `repo` и `pr_number` | Нельзя отличить повтор от сознательной новой Проверки после нового коммита |
| Ключ из `repo`, `pr_number` и SHA коммита на стороне сервиса | Сервису пришлось бы ходить в GitHub ещё до создания Проверки, при недоступном GitHub нельзя даже поставить задачу |
| Хранить ключи в памяти | Теряются при перезапуске, а повтор чаще всего и случается после сбоя |

## Цена решения

- Клиент обязан генерировать ключ, без него запрос отклоняется
- Таблице нужен уникальный индекс и периодическая очистка ключей старше 24 часов
- Повтор через 24 часа создаст новую Проверку

## Условия пересмотра

- Клиенты массово повторяют запросы позже чем через 24 часа
- Появляются клиенты, которые не могут передать заголовок
