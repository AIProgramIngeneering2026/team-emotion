# ADR-0002. Фоновое выполнение Проверки, очередь в таблице БД

- **Дата:** 2026-11-14
- **Статус:** принято

## Контекст и ограничения

- Проверка ходит в GitHub API: при сбое это до 3 попыток по 5 секунд на каждый Tool. Держать HTTP-запрос клиента всё это время нельзя
- GitHub Actions, которые ставят Проверку, ограничены по времени работы
- Проверки не должны теряться при перезапуске сервиса
- Решение ADR-0001: один процесс, без брокера сообщений

## Решение

`POST /checks` сохраняет Проверку в состоянии `queued` и сразу отвечает `201`. Worker в том же процессе раз в секунду забирает из таблицы самую старую Проверку в `queued`, переводит её в `running` и запускает Dispatcher. Клиент узнаёт результат через `GET /checks/{id}` или из комментария в PR.

Если Проверка находится в `running` дольше 10 минут, Worker переводит её в `error` с причиной `timeout`. Так Проверки, прерванные перезапуском, не зависают навсегда.

## Рассмотренные альтернативы

| Вариант | Почему не выбрали |
|---|---|
| Синхронное выполнение внутри `POST /checks` | Запрос может длиться десятки секунд, клиент отвалится по таймауту и повторит запрос, начнутся дубли |
| Очередь в памяти процесса | При перезапуске все `queued` Проверки теряются |
| Отдельный брокер, Redis или RabbitMQ | Ещё один сервис, противоречит ADR-0001 |

## Цена решения

- Клиенту нужно опрашивать `GET /checks/{id}`, результат приходит не сразу
- Опрос таблицы раз в секунду даёт задержку старта до 1 секунды и постоянную небольшую нагрузку на БД
- При переходе на PostgreSQL нужно брать задачу атомарно, `SELECT ... FOR UPDATE SKIP LOCKED`, иначе два Worker возьмут одну Проверку

## Условия пересмотра

- Нужно несколько Worker на разных машинах
- Задержка старта в 1 секунду становится заметной для пользователей
- Опрос таблицы заметно нагружает БД
